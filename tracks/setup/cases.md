# setup — AI에게 환경을 넘기기 전에

사람용입니다. AI가 일을 잘하게 만드는 것의 절반은 프롬프트가 아니라 환경입니다 — 무엇을 물어보고 무엇을 그냥 해도 되는지, 자격증명이 어디 있는지, 지난번에 교정한 것이 다음 세션에도 남는지, 같은 요청을 언제 도구로 굳힐지.

각 항목은 규칙 · 사건 · 행동입니다.

- **유래** — `사건형`은 겪어서 얻은 것, `판단형`은 사건 없이 판단하거나 가져온 것입니다.
- **날짜** — `YYYY-MM-DD`는 사건 일자, `YYYY-MM 기록`은 개별 일자가 남지 않아 기록 시점을 쓴 것입니다.
- **gate 없음** — AI 주입 대상에서 빼고 사례로만 둔 항목입니다. 이유를 항목마다 적었습니다.
- **도구 사실** — 권한 파일의 위치나 패턴 매칭 방식처럼 도구 버전에 딸린 사실은 여기 적지 않고 [adapters](../../adapters/claude-code.md)에 확인일과 함께 둡니다. 여기에는 원리와 사건만 둡니다.
- 빠진 번호 SETUP-20은 공개 전에 폐기한 번호입니다. 다시 쓰지 않습니다. 그 사건(살아 있는 수집기가 32시간 동안 아무것도 수집하지 않은 일)은 automation 트랙 [AUTO-01](../automation/cases.md)로 옮겼습니다.

## 무엇을 물어보게 할 것인가

목표는 하나입니다. **승인 버튼을 누르는 횟수를 0에 가깝게 만들되, 되돌릴 수 없는 사고는 구조적으로 불가능하게.**

### SETUP-01 · "위험해 보이는가"가 아니라 "되돌릴 수 있는가"로 가른다

**행동** 세 층으로 나눕니다.

| 층 | 기준 | 예 |
|---|---|---|
| 차단 | 실행되면 복구 불가, 외부 시스템 파괴 | 원격 삭제 호출, 강제 push, 하드 리셋 |
| 확인 | 복구가 번거롭지만 정당한 쓰임이 분명 | 파일 삭제·이동·이름 변경 |
| 허용 | 위 둘이 아닌 전부 | 읽기, 쓰기, 검색, 스크립트 실행, 웹 조회 |

파일 쓰기가 허용인 이유는 이전 상태가 어딘가에 남기 때문입니다. 그러니 **버전 관리나 백업 같은 되돌림 수단이 있을 때만** 허용에 두고, 없으면 기존 파일 수정은 확인 층으로 옮깁니다. 원격 파괴 호출은 확인이 아니라 차단입니다 — 확인 단계에 두면 습관적인 승인으로 뚫립니다.

조회와 삭제가 같은 주소에서 경로 하나 차이인 시스템을 쓸 때는, 조회 허용이 파괴 호출까지 덮지 않도록 파괴 경로를 따로 차단하세요. 정당한 호출이 가끔 막히면 스크립트로 감싸거나 사람이 직접 하면 됩니다. 정당한 호출이 가끔 불편한 것이 실수로 파괴 호출이 나가는 것보다 훨씬 쌉니다.

설정의 차단 목록과 지침의 문장을 한 쌍으로 두세요. 설정만 있으면 AI가 우회 경로를 찾고, 문장만 있으면 실수를 못 막습니다.

`판단형` · gate SETUP-01 · starter S2가 이 항목의 최소판

### SETUP-02 · "항상 허용"이 어느 파일에 적히는지 먼저 확인한다

**사건** 2026-07-03 "항상 허용"을 눌렀는데 다음에 또 물었습니다. 공유용 프로젝트 설정 파일이 아니라 별도의 로컬 파일에 기록되고 있었습니다.

**행동** 정책을 적어 두는 파일과 실제로 반영되는 파일이 다를 수 있습니다. 규칙을 고치기 전에 승인이 어디에 기록되는지부터 확인하세요. 공통 규칙을 사용자 전체 범위에 두는 설계라면 그곳이 정본이고, 프로젝트 파일로만 운영한다면 두 파일에 같은 규칙을 적어 둡니다.

`사건형` · gate 없음 — 파일 위치는 도구 사실이라 어댑터에 둡니다

### SETUP-03 · 패턴을 넣었는데 계속 묻는다면 매칭 방식부터 의심한다

**사건** (2026-07 기록) 와일드카드를 허용 목록에 넣었는데도 여러 단어짜리 명령과 깊은 경로 명령이 계속 개별 승인을 요구했습니다. 승인 항목만 로컬 파일에 계속 쌓였습니다.

**사건** 2026-08-08 도구 이름만 적는 전체 허용을 두었는데도, 경로가 들어간 복사 명령이 개별 승인 항목으로 쌓였습니다.

**행동** "계속 묻는다"의 첫 번째 용의자는 오타가 아니라 매칭 방식입니다. 와일드카드가 경로 구분자를 넘지 못하는 것으로 보이지만 확정된 메커니즘은 아니고 `[⚠️ 추정·신뢰도 보통]`, 전체 허용 형태도 만능이 아니었습니다. 패턴을 늘리기 전에 도구의 공식 문법을 확인하고, 넣은 뒤에는 실제 명령으로 한 번 시험하세요.

명령을 허용하는 것과 경로를 허용하는 것은 다른 축입니다. 작업이 여러 폴더에 걸치면 상위 작업 폴더를 경로 허용에 등록합니다.

`사건형` · gate 없음 — 매칭 규칙은 도구 사실이라 어댑터에 둡니다

### SETUP-04 · 설정을 고쳤으면 반영되는 시점 이후에 검증한다

**사건** (2026-07 기록) 규칙을 추가했는데 반영이 안 됐습니다. 설정은 세션이 시작될 때 읽히고 있었습니다.

**행동** "추가했는데 안 먹네"라면 문법을 의심하기 전에 설정이 언제 읽히는지 확인하고, 그 시점 이후(대개 새 세션)에 검증하세요. 바꾼 그 세션에서의 확인은 증거가 되지 않습니다.

`사건형` · gate 없음 — 반영 시점은 도구 사실이라 어댑터에 둡니다

### SETUP-05 · 승인 요청이 갑자기 늘면 진단 신호로 본다

**사건** (2026-07 기록) 도구 업데이트 후 승인 요청이 폭증했습니다. 원인이 셋이었습니다 — 새로 생긴 도구가 허용 목록에 없었고, 확장 서버의 이름이 바뀌어 기존 규칙이 죽었고, 작업 경계 밖 경로가 별도의 권한 축이었습니다.

**행동** 짜증이 아니라 진단 신호로 보고 순서대로 확인하세요. 새 도구가 등록됐는가, 확장 이름이 바뀌지 않았는가, 작업 경계가 달라지지 않았는가. 업데이트 직후 점검을 습관으로 만듭니다.

`사건형` · gate SETUP-05

### SETUP-06 · 규칙을 고치기 전에 세션이 실제로 어디서 뜨는지 센다

**사건** 2026-08-04 한 달 동안 프로젝트 설정만 고쳤습니다. 60개 세션을 실제로 세어 보니 48%가 프로젝트 밖에서 뜨고 있었고, 전역 설정에는 권한 블록이 아예 없었습니다. 규칙을 아무리 고쳐도 안 나아지던 이유였습니다.

**행동** 설정에는 사용자 전체와 프로젝트라는 두 범위가 있고, 프로젝트 설정은 그 폴더에서 시작한 세션에만 적용됩니다. 튜닝 효과가 체감되지 않으면 규칙 내용보다 "내 세션들이 실제로 어디서 뜨는가"를 먼저 세세요. 공통 규칙은 전체 범위에 두고, 프로젝트에는 고유분만 얹습니다.

`사건형` · gate 없음 — 범위별 설정 위치는 도구 사실이라 어댑터에 둡니다

### SETUP-07 · 새 패턴은 그 자리에서 승인하고, 끝난 뒤 등록하며, 일부러 묻게 둘 것을 적는다

**행동** 권한 설정을 방치하면 "허용"을 기계적으로 누르는 습관이 생기고, 그 습관이 확인 층을 무력화하는 가장 큰 위협입니다. 새 패턴이 뜨면 일단 승인하고 작업을 마친 다음 등록을 제안받으세요. 추가하기 전에 기존 규칙의 경로 표기 실수인지 먼저 확인합니다.

그리고 **일부러 계속 묻게 둘 것의 목록**도 적어 두세요. 발신, 게시, 상태 변경, 인라인 코드 실행처럼 자주 일어나도 계속 묻는 게 맞는 것들입니다. "왜 이건 허용에 없지?"라고 물을 미래의 자신에게 답을 남기는 것입니다.

**사건** 2026-09-15 자동으로 쌓인 승인 항목 가운데, 브랜치 전환과 작업 중 변경의 폐기를 구분하지 못하는 광역 git 명령 허용이 있었습니다. 차단 목록은 강제 push와 하드 리셋만 막고 있어 이 경로가 비어 있었습니다. 사람이 아니라 설정을 진단하던 AI가 발견했습니다.

`판단형`(응대 루프) · `사건형`(자동 축적 항목) · gate SETUP-07

## 자격증명

### SETUP-08 · 자격증명의 정본은 하나로 두고, 실행 코드는 비밀 값을 직접 들지 않게 한다

**사건** (2026-07 기록) 초기에는 스크립트마다 인증 코드를 복사해 붙였습니다. 자격증명 종류마다 만료 대응이 스크립트별로 어긋나서 디버깅이 지옥이 됐습니다.

**행동** 자격증명의 정본을 한 곳에 두고(저자 환경은 환경 파일이었습니다. OS 키체인이나 비밀 저장소여도 원칙은 같습니다), 외부 호출은 전부 공용 인증 모듈을 거치게 하세요. 그 모듈이 할 일은 셋입니다. 스크립트 위치에서 위로 올라가며 환경 파일을 찾고(스케줄러에서 실행돼도 동작하도록), 로드할 때 필수 키가 있는지 검증하고, 인증 헤더 조립과 갱신까지 포함한 호출 함수를 내보냅니다.

키가 없을 때 "401"로 죽게 두지 말고 "무엇이 없고 어떻게 채우는지"로 실패하게 하세요. 그 메시지는 AI도 읽습니다. 값을 비운 템플릿 파일도 같이 두고 키 이름과 발급 경로와 갱신 주기를 주석으로 적습니다. 자격증명은 종류마다 수명이 다릅니다.

`사건형`(정본 하나 · 모듈 경유) · `판단형`(키체인·비밀 저장소로의 일반화) · gate SETUP-08 · kit [auth-module](kit/auth-module.md), [env-template](kit/env-template.md)

### SETUP-09 · 같은 키가 두 번 선언돼 있지 않은지 본다

**사건** (2026-07 기록) 환경 파일에 같은 계정 키가 두 벌 선언돼 있었습니다. 의도와 다른, 권한 범위가 다른 계정으로 접속되고 있던 것을 한참 뒤에 발견했습니다. 두 계정 다 동작은 했기 때문에 에러가 없었습니다.

**행동** 단순한 로더는 마지막 선언을 조용히 채택합니다. 키를 바꿀 때는 새 줄을 추가하지 말고 기존 줄을 고치세요. 정비할 때 중복 검사를 한 번 돌리면 됩니다.

`사건형` · gate SETUP-09 · kit [env-template](kit/env-template.md)

### SETUP-10 · 자격증명을 설정·예제·문서에 인라인하지 않고, 평문을 찾았으면 재발급까지 한다

**사건** (2026-07 기록) 인증 명령을 매번 승인하기 귀찮아서 허용 규칙에 계정과 비밀번호를 그대로 넣었습니다. 이후 배포하거나 정리할 때마다 설정 파일과 템플릿과 과거 기록에 퍼진 그 값을 추적해서 바꾸는 비용을 반복해서 냈습니다. 넣는 데 5초, 빼는 데 며칠이었습니다.

**사건** 2026-08-10 필드명으로만 찾다가 도구 설정 파일에 들어 있던 평문 키 하나를 놓쳤습니다.

**행동** 환경 변수를 참조하거나 스크립트로 감싸세요. 찾을 때는 필드명만이 아니라 **값의 모양**(키의 고정 머리글자 같은 것)으로도 검색합니다. 평문을 발견했으면 지우는 데서 멈추지 말고 키를 새로 발급하세요 — 과거 백업과 기록에 이미 퍼져 있기 때문입니다 `[판단형 처방 — 재발급까지 한 사건은 확인되지 않았다]`.

같은 이유로 **서명이 포함된 웹훅 주소는 자격증명입니다.** 누구나 익명으로 요청을 보낼 수 있습니다. "그냥 주소잖아"라는 직감이 유출을 만듭니다.

`사건형`(인라인·놓친 키) · `판단형`(재발급) · gate SETUP-10 · kit [credential-sweep](kit/credential-sweep.md)

## 기억

세션은 사라집니다. 세션을 넘어 남길 지식은 덩어리 노트가 아니라 낱개로 저장합니다.

### SETUP-11 · 사실 하나에 파일 하나, 인덱스에 한 줄

**행동** 인덱스 파일에 파일당 정확히 한 줄짜리 포인터를 두고, 실제 내용은 각각의 작은 파일에 둡니다. AI는 세션을 시작할 때 인덱스만 읽고, 관련된 작업이 나오면 그 파일을 펼칩니다. 자동 기억 기능이 없는 도구에서는 같은 구조를 수동으로 운영하고 "시작할 때 인덱스를 읽으라"를 지침에 적어 두면 됩니다.

`판단형` · gate SETUP-11

### SETUP-12 · 교정을 저장할 때는 "왜"와 "다음에 어떻게"를 함께 저장한다

**사건** (2026-07 기록) 이슈 트래커의 상태 이름 "검토중"을 글자 그대로 "사용자가 검토할 것"으로 읽고 브리핑을 잘못 묶었습니다. 실제 의미는 "QA 진행 중"이었습니다. 왜 틀렸는지와 다음에 어떻게 할지를 같이 저장한 뒤로는 재발하지 않았습니다.

**행동** 사실만 저장하면 같은 실수의 변종이 재발합니다. **사실 + 왜 + 다음에 어떻게 쓰나** 세 가지를 함께 적으세요. 저장할 것은 다시 알아내는 비용이 큰 것들입니다 — 만료 주기, 인코딩 함정, 설정이 실제로 어디 반영되는지, 교정 피드백, 문서 어디에도 없는 해석, 반복해야 하는 의무.

## 완료를 믿기 전에

### SETUP-18 · "만들어줘"가 아니라 "만들고, 검증을 통과시킨 결과를 보고해줘"

**사건** (2026-08 기록) AI의 "완료했습니다"를 세 번 믿었다가 세 번 되돌아갔습니다. 문법은 맞는데 경로가 틀렸고, 실행은 되는데 출력이 비어 있었습니다.

**사건** (2026-09 기록) 서로 다른 두 에이전트 도구에서 같은 모양의 보고가 나왔습니다. 한쪽은 데스크톱 브라우저에서 화면 크기만 바꿔 본 것을 "모바일에서 검증했다"고 보고했고, 다른 쪽은 폭이 0인 비정상 화면에서 잰 값을 "배치 순서를 확인했다"고 보고했습니다. 둘 다 검사를 안 한 것이 아니라, **검사하지 않은 범위까지 검사했다고 말한** 것이었습니다. 사용자가 돌아보라고 요청한 뒤에야 드러났습니다.

**행동** 검증을 주문에 넣으면 AI가 스스로 돌리고, 안 넣으면 건너뜁니다. 네 단계면 충분합니다 — 문법 검사, 외부 시스템을 부르면 최소 입력으로 호출 경로만 먼저 확인, 실제로 열어 보거나 실데이터로 한 번 돌려 보기, 일부러 깨뜨려 보기. 그리고 **보고를 "확인함 / 못 봄"으로 나누게** 하세요. "확인함"에는 무엇으로, 어떤 조건에서 확인했는지(도구 · 화면 폭 · 입력값)가 붙어야 합니다. 화면 크기 모의, 실제 기기, 실제 사용자 평가는 서로 다른 검증입니다.

`사건형` · gate SETUP-18 · starter S4와 같은 내용입니다 — starter 경로에서는 S4가, 규칙이 이미 있는 사용자의 격차 진단에서는 이 gate가 봅니다 · kit [breakage-order](kit/breakage-order.md)

### SETUP-19 · 검사 도구는 일부러 깨뜨려 보고 믿는다

**사건** (2026-08 기록) AI가 만든 문서 검사기가 자기 환경의 코드 규약(출력 인코딩 처리)을 지키지 않아 실행하자마자 죽었습니다. 일부러 깨뜨려 보는 과정에서 검사기 자신의 버그 세 건이 그 자리에서 나왔습니다.

**사건** (2026-09-19) 한 작업에서 새로 만든 검사가 **아무것도 검사하지 않고 "0건 · 통과"를 낸 일이 네 번** 있었습니다. 패치 과정에서 정규식의 역참조가 제어 문자로 바뀌어 어디에도 맞지 않았고, 아무도 채우지 않는 변수를 읽어 늘 통과했고, 실패 상황 자체를 만들지 못하는 시험이었고, 화면의 줄바꿈이 아니라 줄바꿈을 뜻하는 표기 글자를 세고 있었습니다. 넷 다 "0건"이 곧 "정상"처럼 보였습니다.

**사건** (2026-09-22) 다른 작업에서 판정 일곱 개를 **하나씩** 깨뜨려 보자, 연도 검사가 사실은 건수 검사에 가려져 있었습니다. 연도를 비운 사본을 넣으면 건수도 줄어 건수 검사가 대신 빨간불을 켰던 것입니다. 도구 전체를 한 번 깨뜨리는 방식이었다면 "잡혔다"로 끝났을 것입니다.

**행동** AI가 만든 테스트가 통과했다는 것은 테스트가 옳다는 증명이 아닙니다. 잡혀야 할 것을 일부러 만들어 넣고 잡히는지 보세요 — **판정 하나마다, 그 판정만 걸리는 사본으로.** 새 검사의 첫 "0건"은 그 확인 전까지 결과가 아니라 가설입니다. 사본은 이전 버전이나 한 줄만 바꾼 복사본이면 충분합니다. 그리고 검사 도구를 주문할 때는 **"이 환경의 코드 규약을 따르라"를 주문에 명시**하세요. 규약 문서가 컨텍스트에 없으면 AI는 자기가 속한 환경의 규약도 따르지 않습니다.

## 반복을 도구로

### SETUP-21 · 같은 요청이 두 번째로 오면 수집 스크립트와 고정 표로 굳힌다

요청자가 원하는 것은 표입니다. 분석과 제안은 따로 요청받았을 때만 붙이세요.

## 코드 안에 코드를 넣을 때

### SETUP-23 · 문자열 안에 코드를 넣는 수정은 이스케이프 층을 먼저 센다

**사건** (2026-09-19 · 2026-09-22) 셸 명령 안의 파이썬 문자열, 그 안의 자바스크립트 템플릿처럼 겹겹이 싸인 곳에 코드를 넣는 수정에서 파손이 여섯 번 났습니다. 두 작업에 걸쳐서였고, 층의 정체는 매번 달랐습니다(템플릿의 줄바꿈, 정규식 역참조, Windows 경로의 역슬래시). 위험한 것은 시끄러운 실패가 아니었습니다 — 한 번은 치환 도구가 경로의 역슬래시를 대문자 변환 지시로 읽어, **성공 코드를 내면서** 파일을 망가뜨렸습니다.

**사건** (2026-09-22) "역슬래시가 섞이면 파일 편집 도구로 직접 넣는다"는 규칙을 세운 뒤에도 두 번 더 났습니다. 이상한 문자를 설명하려고 유니코드 이스케이프 표기를 편집 도구로 적었더니, 도구 호출 자체가 한 번 해석해 **설명하려던 그 문자가 실제로 저장**됐습니다. 사후 검사는 제어 문자만 봐서 이 문자(사적 사용 영역)를 잡지 못했고, 그대로 커밋됐습니다. 따옴표로 막은 셸 heredoc에서도 역슬래시가 하나 줄어 도착했습니다 — 따옴표는 셸 층만 막습니다.

**행동** 코드나 경로를 다른 코드의 문자열 안에 넣기 전에 층을 셉니다 — 셸, 언어의 문자열, 템플릿, 그리고 **AI의 도구 호출 자체.** 둘 이상이거나 역슬래시가 섞이면 파일 편집 도구로 넣되, 넣은 뒤에는 바뀐 파일에서 **제어 문자와 사적 사용 영역(U+E000~F8FF) 문자를 찾아 개수를 보고**하게 하세요. 이스케이프 표기를 문서에서 설명할 때는 역슬래시 없이 `U+F09E`처럼 적습니다. 역슬래시도 따옴표도 없는 한 층짜리 치환이라면 층을 세는 것만으로 충분합니다.
