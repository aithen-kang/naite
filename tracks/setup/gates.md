# setup gates — AI 판정표

AI용. `AI-START.md` 단계 4의 진단표를 채우는 데 쓴다. **이 파일을 사용자 환경에 복사하지 않는다**(AI-START 금지 5).

**전제 환경:** 사용자가 자기 머신에서 AI 에이전트에게 파일 조작·명령 실행·자격증명을 맡긴다. 권한·설정을 스스로 바꿀 수 없는 관리형 환경이면 설정에 기대는 항목이 해당 없음이 된다.

- **트랙 로딩 조건:** 사용자가 AI 에이전트에게 파일 조작·명령 실행·자격증명이 필요한 호출을 맡기거나, 세션을 넘는 기억을 쓰거나, 같은 요청을 반복한다.
- **starter 경로에서는 이 트랙을 열지 않는다** — starter가 이 트랙의 최소판이다(AI-START 단계 3-1).
- **읽는 법:** gate마다 로딩 조건에 해당하는지 본다 → 해당하면 확인 질문으로 사용자 환경을 판정한다 → "안 통하는 상황"에 해당하면 해당 없음.
- **"안 통하는 상황" 칸은 전부 판단에서 왔다** `[⚠️ AI추론]` — 원 기록에 반례 서술이 없다. 사용자 환경에서 반례가 보이면 사용자 쪽이 이긴다.
- **`없음 — 논리형`인 gate**는 반례가 원리적으로 없다는 뜻이다. 해당 없음은 로딩 조건으로만 판정한다.
- **도구 사실은 어댑터에서 확인한다.** 권한 파일 위치·패턴 문법·설정 반영 시점을 이 파일의 문장으로 단정하지 않는다.
- **넣는 형태의 예문은 기준일 뿐이다.** 사용자 지침 파일의 말투로 다듬되 조건과 뜻은 바꾸지 않는다. 끝에 `(naite SETUP-NN · 판)`을 붙인다.
- gate가 없는 항목(SETUP-02·03·04·06·12·15·22)은 주입하지 않는다. 그중 SETUP-22는 starter S1이 사용자 환경에 넣는 경로다.
- **SETUP-18은 starter S4와 같은 내용이다.** 격차 경로에서도 진단되도록 gate를 둔다. 사용자 환경에 `(naite S4 · 판)` 표시가 있으면 SETUP-18은 **있음**이다.

### SETUP-01 · 되돌릴 수 있는가로 세 층

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자가 AI에게 파일 조작이나 명령 실행을 맡긴다 |
| 확인 질문 | 그냥 할 것·물어볼 것·하지 않을 것을 "되돌릴 수 있는가"로 가른 규칙이 있는가? 설정의 차단 목록과 지침 문장이 짝을 이루는가? |
| 검증된 조건 | 쓰기를 허용하는 근거는 되돌림 수단(버전 관리·백업)이다 — 없으면 기존 파일 수정은 확인 층으로 옮겨 제안한다. 조회와 파괴가 같은 주소를 쓰는 시스템이면 파괴 경로를 따로 차단한다 |
| 안 통하는 상황 | AI에게 명령 실행·파일 쓰기를 맡기지 않고 읽기만 시킨다 |
| 넣는 형태 | 지침 세 줄 — starter S2와 같은 문장: "그냥 해도 된다: 읽기, 새 파일 만들기, 결과물 갱신 / 먼저 묻는다: 삭제·이동, 지침·설정 자체의 변경, 외부로 보내기 / 하지 않는다: 되돌릴 수 없는 삭제, 외부 시스템의 삭제 호출" · 설정 — 같은 내용의 차단 목록(문법은 어댑터) |
| 유래 | 판단형 |

### SETUP-05 · 승인 요청 급증은 진단 신호

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자가 권한 설정 파일을 직접 관리한다 |
| 확인 질문 | 승인 요청이 갑자기 늘었을 때 볼 순서(새 도구 미등록 → 확장 이름 변경 → 작업 경계 변화)가 있는가? 도구 업데이트 직후 점검하는 습관이 있는가? |
| 검증된 조건 | 도구 업데이트나 확장 추가가 일어난다 |
| 안 통하는 상황 | 관리형 환경이라 사용자가 권한 설정을 바꿀 수 없다 — 진단해도 고칠 수단이 없다 |
| 넣는 형태 | 지침 한 줄 — 예: "승인 요청이 갑자기 늘면 새 도구 등록 → 확장 이름 변경 → 작업 경계 변화 순서로 원인을 본다. 도구를 업데이트한 직후 한 번 점검한다." |
| 유래 | 사건형 |

### SETUP-07 · 새 패턴 응대 루프와 일부러 묻게 둘 목록

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자가 권한 설정 파일을 직접 관리한다 |
| 확인 질문 | 새 패턴 프롬프트를 "작업 중에는 한 번 승인 → 끝난 뒤 등록 제안 → 등록 전에 기존 규칙의 표기 실수부터 확인"으로 다루는 규칙이 있는가? 일부러 계속 묻게 둘 목록이 적혀 있는가? |
| 검증된 조건 | 승인 버튼을 기계적으로 누르는 습관이 생기면 확인 층이 무력화된다 |
| 안 통하는 상황 | 관리형 환경이라 사용자가 허용 목록을 바꿀 수 없다 — 등록할 곳도, 정리할 자동 축적 항목도 없다 |
| 넣는 형태 | 지침 두 줄 — 예: "새 권한 패턴은 작업 중에는 한 번 승인만 하고, 작업이 끝나면 등록을 제안한다. 등록 전에 기존 규칙의 표기 실수인지 먼저 본다." / "계속 묻게 둘 것: {발신, 게시, 상태 변경, 인라인 코드 실행}" |
| 유래 | 판단형(응대 루프) · 사건형(자동 축적 항목) |

### SETUP-08 · 자격증명 정본은 하나, 실행 코드는 모르게

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자의 스크립트가 외부 서비스 자격증명을 쓴다 |
| 확인 질문 | 자격증명의 정본이 한 곳(환경 파일·OS 키체인·비밀 저장소 중 하나)이고, 스크립트는 공용 인증 모듈을 거쳐서만 외부를 호출하는가? 키가 없을 때 "무엇이 없고 어떻게 채우나"로 실패하는가? 값을 비운 템플릿에 발급 경로·갱신 주기가 적혀 있는가? |
| 검증된 조건 | 자격증명 종류가 둘 이상이거나 만료 주기가 서로 다르다 |
| 안 통하는 상황 | 실행 환경이 역할 기반 인증으로 자격증명을 주입하고 교체까지 맡는다(관리형 런타임의 워크로드 신원) — 코드에도 사용자에게도 비밀 값이 없어 정본을 둘 대상이 없다 |
| 넣는 형태 | 지침 한 줄 — 예: "자격증명의 정본은 {환경 파일 / 키체인 / 비밀 저장소} 한 곳이다. 스크립트는 {인증 모듈}을 거쳐서만 외부를 호출하고 비밀 값을 직접 들지 않는다." · kit `auth-module` · `env-template` |
| 유래 | 사건형(정본 하나 · 모듈 경유) · 판단형(키체인·비밀 저장소로의 일반화 — 저자 환경은 환경 파일뿐이었다) |

### SETUP-09 · 중복 키

| 필드 | 내용 |

### SETUP-10 · 자격증명 인라인 금지와 재발급

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자가 외부 서비스 자격증명을 쓰고, 설정·예제 파일이나 문서를 다른 곳에 공유·백업·동기화한다 |
| 확인 질문 | 자격증명(계정·비밀번호·키·서명이 붙은 웹훅 주소)을 설정·예제·문서에 인라인하지 않는 규칙이 있는가? 평문을 찾을 때 필드명만이 아니라 값의 모양으로도 찾는가? 찾으면 재발급까지를 조치 완료로 보는가? |
| 검증된 조건 | 설정·예제·기록이 공유·백업·동기화되어 한 번 들어간 값이 여러 곳에 남는다 |
| 안 통하는 상황 | 없음 — 논리형: 한 번 퍼진 평문 자격증명은 파일에서 지워도 백업·기록·동기화본에 남아 되돌릴 수 없다(재발급만이 조치다) |
| 넣는 형태 | 지침 두 줄 — 예: "자격증명(계정·비밀번호·키·서명이 붙은 웹훅 주소)은 설정·예제·문서에 적지 않고 환경 변수로 참조한다." / "평문 자격증명을 발견하면 위치를 알리고, 옮긴 뒤 재발급까지를 조치 완료로 본다." · kit `credential-sweep` |
| 유래 | 사건형(인라인·놓친 키) · 판단형(재발급 처방) |

### SETUP-11 · 기억은 낱개 파일과 인덱스 한 줄

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 세션을 넘어 남기는 기억(자동 기억 또는 인덱스 파일)을 쓴다 |
| 확인 질문 | 기억이 "사실 하나에 파일 하나, 인덱스에 한 줄" 구조인가? 자동 기억이 없는 도구라면 "시작할 때 인덱스를 읽는다"가 지침에 있는가? |
| 검증된 조건 | 기억이 늘어 전체를 매번 읽을 수 없다 |
| 안 통하는 상황 | 도구가 기억을 자체 형식으로 관리해 사용자·AI가 기억 파일을 편집할 수 없다 |
| 넣는 형태 | 지침 두 줄 — 예: "기억은 사실 하나에 파일 하나로 저장하고, 인덱스 파일에 파일당 한 줄 포인터를 둔다." / "세션을 시작하면 인덱스만 읽고, 관련 작업이 나오면 해당 파일을 연다." |
| 유래 | 판단형 |

### SETUP-13 · 파일에 있는 것은 기억에 두지 않기

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 세션을 넘어 남기는 기억을 쓴다 |
| 확인 질문 | "작업 파일이 이미 담은 내용은 기억에 저장하지 않는다"는 규칙이 있는가? |
| 검증된 조건 | 원 정보가 AI가 읽을 수 있는 파일에 있다 |
| 안 통하는 상황 | 원 정보가 AI가 세션마다 접근할 수 없는 곳(권한 없는 외부 시스템)에만 있어, 기억 속 사본이 유일한 접근 경로다 |
| 넣는 형태 | 지침 한 줄 — 예: "작업 폴더의 파일이 이미 담고 있는 내용은 기억에 저장하지 않는다. 세션에서만 쓰는 정보도 남기지 않는다." |
| 유래 | 사건형 |

### SETUP-14 · 절대 날짜와 오래된 기억의 대조

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 세션을 넘어 남기는 기억을 쓴다 |
| 확인 질문 | 기억에 쓰는 날짜를 절대 날짜로 바꾸는가? 오래된 기억을 근거로 쓰기 전에 현재 파일·시스템과 대조하라는 문장이 있는가? |
| 검증된 조건 | 기억이 작성 시각 없이 저장된다 |
| 안 통하는 상황 | 기억 항목마다 작성 시각이 자동으로 붙고 AI가 그것을 함께 읽는다 — 이때는 "절대 날짜로" 문장만 제안하지 않고, "대조한 뒤 쓴다"는 그대로 판정한다 |
| 넣는 형태 | 지침 두 줄 — 예: "기억에 쓰는 날짜는 절대 날짜로 바꾼다." / "오래된 기억은 현재 파일·시스템과 대조한 뒤에만 근거로 쓴다." |
| 유래 | 판단형 |

### SETUP-17 · 준비가 안 됐으면 먼저 말하기

### SETUP-18 · 확인까지 주문하고, 확인한 범위만 확인했다고 보고

| 필드 | 내용 |

### SETUP-23 · 문자열 안에 코드를 넣는 수정은 이스케이프 층부터

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 사용자가 AI에게 코드나 경로를 다른 코드의 문자열 안에 넣는 수정을 맡긴다(셸 명령 안의 스크립트, 스크립트 안의 정규식 · 템플릿 · 파일 경로) |
| 확인 질문 | 그런 수정 전에 이스케이프 층(셸 · 언어의 문자열 · 템플릿 · AI의 도구 호출 자체)을 세라는 규칙이 있는가? 넣은 뒤 바뀐 파일에서 제어 문자와 사적 사용 영역(U+E000~F8FF) 문자를 찾아 개수를 보고하게 하는가? |
| 검증된 조건 | 층이 둘 이상이거나 역슬래시가 섞인다. 실패는 에러가 아니라 성공 코드와 함께 파일이 조용히 바뀌는 모양으로 온다 |
| 안 통하는 상황 | 역슬래시도 따옴표도 없는 한 층짜리 치환 — 층을 세는 것만으로 충분하다 |
| 넣는 형태 | 지침 두 줄 — 예: "코드나 경로를 다른 코드의 문자열 안에 넣을 때는 이스케이프 층을 먼저 센다. AI의 도구 호출도 한 층이다. 둘 이상이거나 역슬래시가 섞이면 파일 편집 도구로 넣는다." / "넣은 뒤에는 바뀐 파일에서 제어 문자(개행 · 탭 제외)와 사적 사용 영역(U+E000~F8FF) 문자를 찾아 개수를 보고한다. 이스케이프 표기를 문서에서 설명할 때는 역슬래시 없이 U+XXXX로 적는다." · 검사 예(파이썬 한 줄, 역슬래시 없이 쓴 판): `python -c "import sys;t=open(sys.argv[1],encoding='utf-8').read();print(sum(1 for c in t if (ord(c)<32 and ord(c) not in (9,10,13)) or 0xE000<=ord(c)<=0xF8FF))" 파일` |
| 유래 | 사건형 |
