# kit · breakage-order — 검증을 주문에 넣는 문장과 파손 테스트

- **조건:** AI에게 스크립트·검사 도구·테스트를 만들게 하고, 그 결과로 무언가를 결정한다
- **도구 의존:** 없음
- **쓰는 ID:** SETUP-19 (주문 문장은 starter S4 · SETUP-18과 같다)

## 1. 주문 문장

"만들어줘"로 끝내면 AI는 검증을 건너뛴다. 검증이 주문에 있으면 스스로 돌린다.

```
만들고, 아래 네 단계를 통과시킨 결과까지 보고해 줘.
1. 문법 검사
2. 외부 시스템을 부른다면 최소 입력으로 호출 경로만 먼저 확인
3. 실제로 열어 보거나 실데이터로 한 번 실행
4. 검사·테스트 도구라면 잡혀야 할 결함을 일부러 넣어 잡히는지 확인
이 폴더의 코드 규약({규약 문서 경로})을 따른다.
```

마지막 줄이 빠지면, 규약 문서가 컨텍스트에 없는 AI는 자기가 속한 환경의 규약도 따르지 않는다. 검사 도구가 출력 인코딩 규약을 안 지켜 실행하자마자 죽은 사례가 여기서 나왔다.

## 2. 파손 테스트 설계

검사 도구를 믿으려면 **임시 사본에서** 일부러 깨뜨려 본다. 원본은 건드리지 않는다.

| 넣을 결함 | 기대하는 결과 |
|---|---|
| 검사가 잡아야 할 위반을 하나씩 넣는다 | 위반마다 해당 항목으로 보고되고, 실패 코드로 끝난다 |
| 결함 없는 원본 | 통과 한 줄, 성공 코드 |
| 잘못된 입력 경로·빈 입력 | "무엇이 틀렸고 어떻게 고치나"가 담긴 사용법 오류, 위반과 다른 코드 |
| 실패인데 결과물을 쓰는 모드 | 아무것도 쓰지 않는다 |

## 3. 알아 둘 것

- **종료 코드만 보지 말고 기대한 메시지가 나왔는지도 함께 본다.** 결함을 넣었더니 기대한 실패 코드가 나왔는데, 알고 보니 설계대로 멈춘 것이 아니라 다른 곳에서 난 예외 크래시였던 사례가 한 번 있다. 인터프리터는 처리하지 않은 예외에도 같은 실패 코드를 돌려줄 수 있다. 가능하면 스크립트의 실패 코드를 인터프리터가 쓰는 번호와 겹치지 않게 둔다. (1회 사례 — 규칙 아님)
- AI가 만든 테스트가 통과했다는 것은 테스트가 옳다는 증명이 아니다. 파손 테스트만이 그것을 보여 준다.
