# spec gates — AI 판정표

AI용. `AI-START.md` 단계 4의 진단표를 채우는 데 쓴다. **이 파일을 사용자 환경에 복사하지 않는다**(AI-START 금지 5).

**전제 환경:** 문서를 받아 다른 산출물을 만드는 사람이나 AI가 있는 자리다. SPEC-08 · 12는 시스템·코드의 실행되는 정의를 읽을 수 있어야, SPEC-09 · 10 · 11 · 13은 대상을 직접 조회할 수 있어야 판정된다 — 문서만 오가는 환경이면 나머지 항목만 해당한다.

- **트랙 로딩 조건:** 사용자가 AI와 함께 기획·정책·보고·위키 문서를 쓰거나 유지한다.
- **읽는 법:** gate마다 로딩 조건에 해당하는지 본다 → 해당하면 확인 질문으로 사용자 환경을 판정한다 → "안 통하는 상황"에 해당하면 해당 없음.
- **"안 통하는 상황" 칸은 전부 판단에서 왔다** `[⚠️ AI추론]` — 원 기록에 반례 서술이 없다. 사용자 환경에서 반례가 보이면 사용자 쪽이 이긴다.
- **넣는 형태의 예문은 기준일 뿐이다.** 사용자 지침 파일의 말투로 다듬되 조건과 뜻은 바꾸지 않는다. 끝에 `(naite SPEC-NN · 판)`을 붙인다. 판은 `CHANGELOG.md` 맨 위의 판이다.
- **`없음 — 논리형`인 gate**(SPEC-09·10·11·13)는 반례가 원리적으로 없다는 뜻이다. 해당 없음은 로딩 조건으로만 판정한다.

### SPEC-01 · 구조 먼저, 상세는 확정 후

| 필드 | 내용 |

| 확인 질문 | "뼈대(목록·상태값)를 먼저 확정받고 상세를 쓴다", "확정한 구조를 임의로 바꾸지 않는다"에 해당하는 규칙이 있는가? |

### SPEC-08 · 문서보다 시스템

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 운영 중인 시스템·데이터를 설명하는 문서가 있고, 그 위에 기획·개선안을 쌓으려 한다 |
| 확인 질문 | 문서가 시스템 구조를 주장하면 쌓기 전에 실물을 확인하라는 규칙, 충돌 시 서열(실제 시스템 > 코드 > 문서)이 있는가? 서열을 적용하기 전에 두 진술이 같은 질문·같은 축에 답하는지 보게 하는가? |
| 검증된 조건 | 실물(시스템·코드·데이터)에 읽기 접근이 있다. 접근이 없으면 실물 확인을 담당자 확인으로 대신하고, 그 사실이 어느 등급으로 확인됐는지 표시한다 |
| 안 통하는 상황 | 문서가 곧 실물인 영역(약관·계약·법령) — 시스템이 문서를 구현하는 쪽이다 |
| 넣는 형태 | 지침 두 줄 — 예: "문서가 시스템 구조를 주장하면, 그 위에 무언가를 쌓기 전에 실물에서 확인한다. 충돌하면 값·상태는 실제 시스템, 로직은 코드가 문서를 이긴다." / "서열이나 대체를 적용하기 전에 두 진술이 같은 질문·같은 축(시점·매체·장소·주체)에 답하는지 먼저 본다." · 절차는 kit `reverse-spec` |
| 유래 | 사건형 |

### SPEC-11 · "없다"는 전수로만

### SPEC-13 · 이전 결론과 조사 권고는 실행 전에 대상에서 확인

| 로딩 조건 | 문서가 외부 시스템·데이터·다른 사람의 상태에 관한 사실을 적는다 |
| 확인 질문 | 관찰한 사실에 확인 날짜를 붙이는 규칙이 있는가? |
| 검증된 조건 | 사실의 대상이 문서와 무관하게 변한다 |
| 안 통하는 상황 | 관찰이 아니라 결정을 적는 문서(정책 규칙 자체) — 시점은 버전과 변경 기록이 맡는다 |
| 넣는 형태 | 지침 한 줄 — 예: "시스템·데이터에서 확인한 사실에는 확인한 날짜를 붙인다(예: 확인 기준 2026-09-15)." · 표기는 kit `tags` |
| 유래 | 사건형 |

### SPEC-15 · 현재와 개선안을 나란히 쓰지 않기

| 필드 | 내용 |

| 확인 질문 | 본문은 현행만 적고, 변화 방향은 상태 컬럼·임시 섹션·변경 기록으로 분리하는 규칙이 있는가? |
| 검증된 조건 | 문서가 출시 뒤에도 그 대상의 정의로 계속 쓰인다 |
| 안 통하는 상황 | 출시 뒤 폐기되는 일회성 과제 문서 |
| 넣는 형태 | 문서 템플릿 조각 — kit `living-doc` |
| 유래 | 사건형 |

### SPEC-16 · 문서가 많아지면 대조는 스크립트

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 서로 참조하는 문서가 다섯 개를 넘는다 |
| 확인 질문 | 링크·절 참조·항목 수를 대조하는 스크립트가 있는가? 새 규칙을 만들 때 어긋나는 기존 문서를 찾게 하는가? 절 참조에 대상 문서를 붙이는 표기 규율이 있는가? |
| 검증된 조건 | 검사기는 표기(링크·번호)만 잡고, 문서끼리 규칙이 모순되는 것은 못 잡는다. 절 참조 검사는 쓰는 쪽이 대상 문서를 붙인다는 표기에 기댄다 — 문서 이름을 생략한 참조가 자기 문서의 같은 번호와 맞으면 틀린 채 통과한다 |
| 안 통하는 상황 | 문서들이 하나의 입력에서 매번 다시 생성되는 파생물 — 대조할 곳이 생성기 하나로 줄어든다 |
| 넣는 형태 | 스크립트 — kit `hygiene-prompt`로 사용자 환경에서 만들게 한다 · 지침 한 줄 — 예: "다른 문서의 절을 가리킬 때는 문서 이름을 항상 붙이고, 범위·복수 표기는 한 덩어리로 쓴다. 새 규칙을 만들면 어긋날 수 있는 기존 문서를 같이 고친다." |
| 유래 | 사건형 |

### SPEC-17 · 지시문과 폐기값을 남기지 않기

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 문서를 다른 사람이나 다른 AI(다음 세션의 AI 포함)에게 넘긴다. 또는 AI가 값 · 선택 · 구조를 바꾸는 작업을 하고 완료를 보고한다 |
| 확인 질문 | 넘기기 전에 작업 지시문 잔존 · 본문에서 확정한 항목의 미정 목록 잔존 · 폐기값 잔존을 확인하는 절차가 있는가? 바꾸는 작업의 완료 보고에 **옛 값을 찾은 검색어와 결과 건수**를 붙이게 하는가 — "확인했다"는 말이 아니라? |
| 검증된 조건 | 받는 쪽이 문서의 문장을 그대로 실행 대상으로 읽는다. 같은 취지의 규칙을 지침에 적어 두고도 옛 값이 남는 일이 반복됐다 — 문장만으로는 막히지 않았다 |
| 안 통하는 상황 | 지시문 자체가 산출물인 문서(인수인계 메모·프롬프트 파일). 새 파일만 만든 작업, 한 파일의 한 곳만 고친 작업 — 옛 값이 남을 자리가 없다 |
| 넣는 형태 | 체크리스트 — kit `pre-handoff-check` · 지침 한 줄 — 예: "값 · 선택 · 구조를 바꾼 작업은 완료를 보고하기 전에, 건드린 문서와 그 문서를 참조하는 문서에서 옛 값을 검색하고 검색어와 결과 건수를 보고에 붙인다." |
| 유래 | 사건형 |

### SPEC-18 · 자동 전체 재게시 금지

| 필드 | 내용 |
|---|---|
| 로딩 조건 | 로컬 문서를 위키·게시판·CMS에 올리고, 올린 뒤 사람이 게시본을 손본다 |
| 확인 질문 | 게시가 사람 확인 뒤 해당 부분만 이뤄지는가? 덮어쓰기 스크립트에 명시적 허가 없이는 종료되는 가드가 있는가? |
| 검증된 조건 | 게시본에 사람의 손질이나 댓글이 붙는다 |
| 안 통하는 상황 | 사람이 손대지 않는 순수 파생 뷰(생성기가 매번 다시 만드는 페이지) |

| 유래 | 사건형 |

### SPEC-19 · AI 문서의 검증 상태

| 필드 | 내용 |
|---|---|
| 로딩 조건 | AI가 쓴 문서가 다른 사람·다른 AI가 근거로 읽는 곳에 놓인다 |
| 확인 질문 | 문서 상단에 검증 상태를 적고, 검증 전 초안은 정본에서 링크·인용하지 않는 규칙이 있는가? |
| 검증된 조건 | 읽는 AI가 언급된 문서를 믿을 만한 것으로 취급한다 |
| 안 통하는 상황 | 사람 검토 승인을 거쳐야만 저장소에 들어가는 흐름 — 저장소에 있다는 사실이 곧 검증 상태다 |
| 넣는 형태 | 지침 한 줄 — 예: "AI가 쓴 문서 상단에 '검증됨' 또는 'AI 초안 — 검증 전'을 적는다. 검증 전 초안은 정본 문서에서 링크하거나 인용하지 않는다." |
| 유래 | 판단형 |
