# kit · domain-skeleton — 정책 문서 골격

- **조건:** 한 도메인(서비스 영역)의 규칙을 한 문서에 완결해 쓰고, 그 문서를 AI가 읽는다
- **도구 의존:** 없음
- **쓰는 ID:** SPEC-01 · SPEC-02

예시는 가상의 정기배송 구독 앱이다.

## 범위 선언 — 문서 맨 위

```markdown
> ⚠️ **이 파일의 범위**
> - ✅ 포함: 비즈니스 로직, 도메인 고유 정책, 상태값, 예외 처리, 시스템 메시지
> - ❌ 제외: 레이아웃, 간격, 색상, 플랫폼별 UI 제약 (→ {정보 구조 문서})
```

이 선언이 없으면 문답 중에 "버튼은 하단 고정인가요?" 같은 레이아웃 질문이 섞여 들어오고, 문서가 정책과 디자인 스펙의 잡탕이 된다.

## 골격 — 10개 섹션

| 섹션 | 내용 | 필수 여부 |
|---|---|---|
| 1 도메인 개요 | 서비스 영역과 주요 기능 1~3문장 | 필수 |
| 2 공통 규칙 | 접근 권한·저장 방식·오류 처리 같은 공통 규칙 표. 개별 규칙이 없으면 이것이 기본값 | 필수 |
| 3 상태값 정의 | 상태 그룹별 코드와 설명 표. 전 문서·전 산출물이 같은 코드를 쓰게 하는 장치 | 선택 (없으면 삭제) |
| 4a 단위별 정책 | 화면·기능 단위의 정책, 진입과 이탈, 예외 처리 | 필수 |
| 4b 횡단 정책 | 두 단위 이상에 걸치는 정책. 정책 ID(POL-NN) 매트릭스 | 선택 (없으면 매트릭스 비움) |
| 5 분기 정책 | 플랫폼·지역별로 동작이 갈리는 항목 표 | 선택 (분기 없으면 삭제) |
| 6 시스템 메시지 | 메시지 문구 + 발생 조건 + 출력 유형 | 선택 (없으면 삭제) |
| 7 변경 로그 | 날짜·변경 항목·한 줄 요약. 본문에는 최신 규칙만 | 필수 (처음엔 빈 표) |
| 8 섹션 성숙도 | 섹션별 확정·초안과 최종 갱신 — kit `doc-header` | 여러 세션에 걸치면 필수 |
| 9 미정 사항 | 본문의 `[⚠️ TBD]`를 한 곳에 모으고 우선순위를 매긴다 | 필수 (없으면 빈 표) |

## 공통 기반을 먼저 — 단위별 정책을 쓰기 전에

| 항목 | 역할 |
|---|---|
| 용어 사전 | 상태값 코드·화면 용어 통일. "멈춤"·"일시정지"·"홀드"가 섞이지 않게 |
| 계정·프로필 체계 | 모든 단위의 전제 조건 |
| 외부 연동 규칙 | 결제·배송 조회 같은 외부 의존의 제약 |
| 교차 정책 | 권한·등급처럼 여러 단위에 흩어지는 정책의 원본 |
| ID 체계 | 전체 단위 ID를 미리 예약해 참조 충돌을 막는다 |
| 상태값 코드 | 핵심 엔티티 분류 |

이 표가 섹션 2와 3을 먼저 확정하는 것과 같다. 여기서 만든 기반은 같은 서비스의 다른 도메인 문서에 그대로 재사용된다.

## 상태값 표 예

| 상태값 | 설명 | 비고 |
|---|---|---|
| ACTIVE | 구독 유지 중, 다음 결제 예약됨 | |
| PAUSED | 일시정지. 결제·배송 중단, 최대 90일 | 90일 초과 시 자동 CANCELED |
| CANCELED | 해지. 남은 이용 기간 종료 시 EXPIRED | |
| EXPIRED | 이용 종료. 재구독만 가능 | |

문서 말미에 한 줄: *"이 파일은 작업 중 새 정책이 발견될 때마다 갱신하는 살아 있는 문서다."*
