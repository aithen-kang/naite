# kit · living-doc — 과제가 끝나도 죽지 않는 문서

- **조건:** 운영 중인 대상의 문서에 개선안을 함께 적고, 그 문서가 출시 뒤에도 그 대상의 정의로 계속 쓰인다
- **도구 의존:** 없음
- **쓰는 ID:** SPEC-15

## 1. 썩는 구조와 버티는 구조

문서의 주어를 "이번 과제"가 아니라 "이 화면·이 도메인"으로 둔다. 개편은 그 문서를 통과해 가는 하나의 사건일 뿐이다.

❌ 썩는 구조 — 출시되는 순간 TO-BE가 AS-IS가 되는데 아무도 컬럼을 옮겨 적지 않는다.

| 항목 | AS-IS | TO-BE |
|---|---|---|
| 해지 확인 | 확인 다이얼로그 1회 | 사유 선택 추가 |

✅ 버티는 구조 — 본문은 현행만, 변화 방향은 상태 컬럼이 담는다.

| 항목 | 정의 | 상태 |
|---|---|---|
| 해지 확인 | 해지 요청 시 확인 다이얼로그 1회 | 변경검토 (사유 선택 추가 검토 중) |
| 배송 메모 | 배송지별 자유 입력 1건 | 유지 |
| 선물 포장 옵션 | 결제 단계의 포장 선택 | 제거예정 |

상태값은 넷으로 고정한다: `유지` / `변경검토` / `제거예정` / `신규예정`. 출시 뒤 할 일은 상태를 `유지`로 돌리고 정의를 고치는 것뿐이다.

## 2. 문서에 두는 세 장치

```markdown
## {본문 — 현행 정의}
(현행 확정 사실만. "현재", "기존", "이전" 같은 시제 표현을 쓰지 않는다.
 시점이 필요하면 "~한다(YYYY-MM 기준)"으로 박는다.)

| 항목 | 정의 | 상태 |
|---|---|---|

## 진행 중 변경 (in-flight)
> 이 섹션은 출시되면 비운다. 살아남아야 할 내용은 본문 정의로 흡수하고, 나머지는 변경 기록 한 줄로 줄인다.

- 과제: {이름}
- 배경·단계·미결: {…}

## 변경 기록
| 날짜 | 변경 | 요약 |
|---|---|---|
```

## 3. 갱신 시점을 박아 둔다

- **출시 시점** = 진행 중 변경 섹션 비우기 + 상태 컬럼 정리 + 변경 기록 한 줄. 출시 체크리스트의 한 항목으로 만든다.
- 이 정리는 기계적인 작업이라 AI에게 맡기기 좋다 — "출시됐으니 이 문서의 진행 중 변경을 접고 상태를 정리해 줘." 사람은 검수한다.
- 문서가 여러 개로 자라면 갱신 약속만으로는 문서끼리 어긋난다. 대조를 스크립트로 한다(SPEC-16).
