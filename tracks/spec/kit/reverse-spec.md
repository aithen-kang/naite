# kit · reverse-spec — 운영 중인 시스템을 문서로 만들 때

- **조건:** 운영 중인 시스템을 문서로 만들거나, 기존 문서 위에 개선안을 쌓기 전. 시스템·코드에 **읽기** 접근이 있다. 접근이 없으면 실물 확인을 담당자 확인으로 대신하고 그 등급을 표시한다
- **도구 의존:** 없음 (조회 도구는 사용자 환경의 것)
- **쓰는 ID:** SPEC-08 · SPEC-09 · SPEC-10 · SPEC-11 · SPEC-12 · SPEC-13

## 1. 세 소스 — 각자 다른 방식으로 틀린다

| 소스 | 강점 | 약점 |
|---|---|---|
| 실제 시스템(읽기 전용 조회) | 지금 이 순간의 값·개수·상태 | 로직이 안 보인다. 조회 경로를 잘못 짚으면 오판한다 |
| 코드 | 노출 조건·검증 규칙 같은 로직 | 읽기 어렵고 양이 많다. 배포 안 된 버전을 볼 수 있다 |
| 기존 문서·위키 | 의도·배경·용어. 탐색의 출발점 | 낡는다. 확인 날짜 없는 문서는 믿을 수 없다 |

## 2. 절차

1. **문서로 지도를 그린다.** 산출물은 "확인할 주장 목록"이지 사실이 아니다.
2. **코드에서 주장을 하나씩 대조한다.** 일치 / 불일치 / 미확인으로 판정한다.
3. **실제 시스템을 읽기 전용으로 조회한다.** 개수·필드·실데이터·영향 범위를 실물에서 센다. 원자료는 보존해 두면 재조회 없이 재분석할 수 있다. **쓰기 호출은 하지 않는다** — 도구 권한과 지침 문장 양쪽에 막아 둔다.
4. **충돌하면 서열대로 판정한다.** 값·개수·현재 상태는 실제 시스템 > 코드 > 문서. 로직·조건은 코드 > 실제 시스템 > 문서. 문서가 이기는 경우는 없다.
5. **판정 결과를 적는다.** 사실마다 근거(코드 위치·조회 경로·확인 날짜)를 남긴다. 이전 결론을 뒤집었으면 `★정정`으로 드러낸다.

## 3. 점검표 — 결론을 적기 전에

```
□ 서열을 적용하기 전에, 두 진술이 같은 질문·같은 축에 답하는지 봤나      (SPEC-08)
□ 개수는 한 페이지 분량이 아니라 총계 필드로 셌나                        (SPEC-09)
□ "없다"고 적기 전에, 조회 경로 자체가 맞았음을 입증했나                  (SPEC-10)
□ 부재는 전수 확인 뒤에만 적었나 — 있다는 건 하나로, 없다는 건 전부로     (SPEC-11)
□ 타입·권한·상태값 목록은 문서가 아니라 실행되는 정의에서 뽑았나          (SPEC-12)
□ 이전 세션의 결론, 조사를 맡긴 AI의 권고를 실행 전에 대상에서 확인했나   (SPEC-13)
□ 리스크 등급은 "이상하다"가 아니라 "그 이상함을 실제로 쓰는 곳"으로 판정했나 (SPEC-13)
□ 이전 결론과 어긋난 것을 조용히 덮지 않고 ★정정으로 남겼나              (SPEC-13)
□ 확인한 사실마다 확인 날짜가 있나                                        (SPEC-14)
```

## 4. AI에게 시키는 문장

```
이 문서의 시스템 주장을 목록으로 뽑고, 각각을 코드와 실제 시스템(읽기 전용)에서 확인해
일치 / 불일치 / 미확인으로 판정해 줘.
- 쓰기·삭제 호출은 하지 않는다.
- 충돌하면 값·상태는 실제 시스템, 로직은 코드를 따르고, 한쪽을 지우지 말고 병기한다.
- "없다"는 판정은 조회 경로가 맞았음을 먼저 보인 뒤에만 한다.
- 이전 결론과 어긋나면 ★정정으로 표시한다.
- 확인한 사실마다 확인 날짜를 붙인다.
```
